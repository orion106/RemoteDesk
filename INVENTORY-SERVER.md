# Общая инвентаризация: установка на TrueNAS

Служба принимает подключения Windows-клиентов по HTTPS. В каталоге SSD dataset находятся `inventory.db`, фотографии и конфигурация. Только эта служба открывает SQLite; клиентам не требуется SMB-доступ к базе. Не переносите файл SQLite на сетевую шару Windows и не запускайте второй экземпляр службы на том же dataset.

## Сборка и поставка

Из корня исходного проекта на машине с работающим Docker Engine для Linux:

```powershell
docker build -f deploy/inventory.Dockerfile -t remoteassist-inventory:1.1 .
docker save -o remoteassist-inventory-1.1.tar remoteassist-inventory:1.1
```

Образ не содержит личный Excel, реальную базу, фотографии, сертификаты или пароли. Отдельная публикация сервера без Docker:

```powershell
dotnet publish RemoteAssist.Inventory.Server/RemoteAssist.Inventory.Server.csproj -c Release -r linux-x64 --self-contained false -o artifacts/inventory-server-linux-x64
```

Для неё нужен ASP.NET Core Runtime 10; контейнер уже включает runtime. Windows-приложение использует отдельную Windows-сборку. Исходники Dockerfile и YAML являются воспроизводимой конфигурацией образа: успешная `dotnet publish` сама по себе не означает, что Docker-образ собран или проверен в TrueNAS.

Если Linux-публикация уже собрана, можно упаковать её без повторного скачивания SDK-образа. Контекстом сборки должен быть **только чистый каталог Linux-публикации**, без рабочей базы и личных файлов:

```powershell
docker build -f deploy/inventory.prebuilt.Dockerfile -t remoteassist-inventory:1.1 artifacts/inventory-server-linux-x64
```

## Подготовка dataset и HTTPS

1. В TrueNAS создайте SSD dataset, например `/mnt/SSD_POOL/remoteassist-inventory`, и HDD dataset `/mnt/HDD_POOL/remoteassist-inventory-backups`. Подставьте реальные имена пулов. Дайте UID/GID `1654:1654` доступ чтения и записи только к этим двум каталогам. Каталог резервных копий должен быть вне рабочего dataset.
2. В SSD dataset создайте `config`. Поместите туда `server.pfx` с закрытым ключом и сертификатом на выбранное DNS-имя NAS, а также `tls-password.txt` с паролем PFX. Сертификат должен быть доверенным на рабочих ПК; для внутреннего центра сертификации установите его корневой сертификат на клиенты. Windows-клиент не отключает проверку TLS. Если PFX без пароля, файл `tls-password.txt` должен быть пустым.
3. Создайте `config/owner-password.txt` с начальным паролем владельца длиной не менее 12 символов. Служба читает его только при пустой базе, создаёт личную учётную запись `owner` и сохраняет только PBKDF2-SHA512-хеш со случайной солью. Это пароль приложения, не пароль TrueNAS. Дайте доступ к этим файлам только владельцу системы и UID 1654. После первого запуска исходный файл начального пароля можно убрать; работающая база больше в нём не нуждается.
4. Сохраните YAML приложения и выбранные пути/имя хоста отдельно в `config/deployment-notes.txt`, без повторного копирования паролей в заметки. Каталог `config` включается в резервные копии вместе с сертификатом. Ограничьте доступ к HDD-копиям так же, как к рабочему dataset.

Контейнер работает как пользователь 1654 без дополнительных Linux-возможностей, с файловой системой образа только для чтения. Записываются только `/data`, `/backups` и временный `/tmp`. Фото ограничены 20 МБ, проверяются сигнатуры JPEG/PNG, хранятся под серверными GUID; исходное имя файла не используется как путь.

## Установка Custom App

1. Доставьте собранный `remoteassist-inventory-1.1.tar` на NAS и загрузите образ командой `docker load -i <полный-путь-к-архиву>` в Shell TrueNAS. Альтернатива — собственный контейнерный registry: замените `image` на его адрес и `pull_policy` на `missing` в YAML. Настройка registry и обновление TrueNAS не входят в установку этой службы.
2. Откройте Apps → Discover Apps → меню установки пользовательского приложения → Install via YAML. Используйте `deploy/truenas-inventory.yaml`, заменив `SSD_POOL`/`HDD_POOL` и при необходимости порт/имя образа. Для импортированного локального образа оставьте `pull_policy: never`.
3. Запустите приложение. При первом запуске необходимы файл пароля владельца и TLS-сертификат. В журнале не должно быть ошибок прав доступа или сертификата. Файл `inventory.lock` предотвращает параллельный запуск двух служб на одной базе; файл можно сохранять между перезапусками — важна открытая блокировка процесса, а не наличие файла.
4. Проверьте с рабочего ПК `https://имя-nas:8443/api/health`: ответ `status: ok`, `service: RemoteAssist.Inventory`, `version: 1`. Этот endpoint не раскрывает данные и не требует входа. Все прочие методы, кроме `/api/login`, требуют действительный Bearer-сеанс.
5. В разделе «Инвентаризация» Windows-программы задайте адрес `https://имя-nas:8443`, войдите как `owner`, создайте личные аккаунты администраторов. У каждого своя локальная связь с карточками ПК; пароли удалённого доступа не отправляются в эту базу.

Для изолированной разработки допускается `INVENTORY_ALLOW_HTTP=true` на loopback. Этот флаг отсутствует в производственном YAML. Вход ограничен восемью попытками в минуту с одного IP. Сеансы действуют 12 часов, хранятся только их SHA-256-хеши; смена пароля, отключение пользователя или изменение роли отзывает его сеансы.

## Резервные копии и восстановление

Служба создаёт согласованную копию при запуске и затем каждые 24 часа. Пока фиксируется копия, операции изменения данных кратковременно ожидают. SQLite копируется через Backup API, затем копируются неизменяемые файлы фотографий и `config`, создаётся манифест SHA-256 и проверяются целостность базы и наличие всех фотографий. Только проверенная копия получает имя `inventory-…`; сохраняются последние 14 завершённых копий. Ошибка отображается в журнале и в статусе резервных копий владельца, не вызывает удаления рабочих данных. Незавершённые `.pending-…` не используются для восстановления и не считаются завершёнными копиями.

Проверка конкретной копии выполняется утилитой из того же образа (пути host замените на свои):

```sh
docker run --rm --user 1654:1654 --volume /mnt/HDD_POOL/remoteassist-inventory-backups:/backups:ro remoteassist-inventory:1.1 verify-backup /backups/inventory-ИМЯ-КОПИИ
```

Восстановление:

1. Остановите Custom App. Сохраните прежний dataset для возможности возврата. Создайте **новый пустой** SSD dataset, например `/mnt/SSD_POOL/remoteassist-inventory-restored`, с теми же правами. Восстановление в непустой каталог утилита отклоняет.
2. Проверьте выбранную копию предыдущей командой. Восстановите в новый dataset:

```sh
docker run --rm --user 1654:1654 --volume /mnt/HDD_POOL/remoteassist-inventory-backups:/backups:ro --volume /mnt/SSD_POOL/remoteassist-inventory-restored:/restore remoteassist-inventory:1.1 restore /backups/inventory-ИМЯ-КОПИИ /restore
```

3. В YAML замените source у `/data` на новый dataset. Убедитесь, что сертификат и пароль сертификата восстановлены в `config`, и запустите приложение. При восстановлении аннулируются старые сеансы; пользователи входят заново и получают полный актуальный снимок. `InstanceId` и GUID имущества сохраняются, поэтому локальные связи с карточками ПК остаются действительными. Не используйте восстановленную копию как независимую вторую базу одновременно с исходной.
4. Проверьте вход двумя учётными записями, число кабинетов/объектов, открытие нескольких фотографий и экспорт завершённой проверки. Зафиксируйте дату учебного восстановления в журнале администрации. Старый dataset удаляется только после отдельного решения администратора.

## API и совместная работа

Контракты: `RemoteAssist.Inventory/Contracts.cs`. Все времена API — ISO 8601, идентификаторы — GUID-строки. Значения `Version=0` обозначают создание, изменения требуют текущую версию. Ошибка `409` содержит `ApiError` и текущую запись: клиент сохраняет свой черновик и предлагает перечитать данные. Статус `401` требует повторного входа, `403` — прав владельца. Сервер не применяет неподтверждённые перемещения из результатов инвентаризации.

| Метод | Назначение |
|---|---|
| POST `/api/login`, POST `/api/logout`, GET `/api/me` | Личный сеанс |
| GET `/api/snapshot` | Полная согласованная копия, `InstanceId`, `Revision`, даты и история |
| POST `/api/rooms`, `/api/assets`, `/api/cartridges`, `/api/photos` | `SaveCommand<T>` с `CommandId` и `Value`, оптимистическая версия |
| POST `/api/rooms/seed` | Добавление отсутствующих кабинетов карты по точному корпусу и номеру |
| POST `/api/import` | Атомарный подтверждённый импорт; SHA-256 файла защищает от повторного импорта |
| POST `/api/cartridges/replace` | Атомарное снятие/установка с версиями принтера и обоих экземпляров |
| POST `/api/audits`, `/api/audits/items`, `/api/audits/add-asset`, `/api/audits/complete` | Создание снимка, сверка, добавление обнаруженного имущества, фиксация |
| POST `/api/photos/upload` | multipart: `file`, `ownerType` (`asset`, `room`, `auditItem`), `ownerId`, `caption`, `commandId` |
| GET `/api/photos/{id}/content` | Защищённый файл фотографии |
| GET/POST `/api/users` | Список/изменение пользователей, только owner |
| GET `/api/backups/status`, POST `/api/backups` | Статус и ручная резервная копия, только owner |

Идемпотентные команды сохраняются в SQLite вместе с результатом; повтор после обрыва связи должен отправлять тот же `CommandId` и тело. Повторный `CommandId` с другим телом отклоняется. Ручной запрос резервной копии не идемпотентен: каждый запуск создаёт отдельную проверенную копию. Клиент обновляет снимок каждые 30 секунд и после изменений. Завершённые проверки содержат собственные снимки реквизитов и наименований кабинетов; их выгрузка не зависит от последующих изменений реестра.

В этой версии записи реестра и история сохраняются как транзакционный JSON-снимок в SQLite, учётные записи, сеансы и результаты команд — в отдельных таблицах. Это решение рассчитано на один учебный корпус и небольшое число одновременно работающих администраторов. История не обрезается. Для сильно выросшей базы нужно измерять время выдачи полного снимка и размер резервной копии перед расширением на несколько корпусов.

## Проверки разработчика

```powershell
dotnet run --project RemoteAssist.Inventory.Server.Tests/RemoteAssist.Inventory.Server.Tests.csproj
```

Набор проверяет реальный HTTP-сервер с двумя клиентами, права, пароли и сеансы, конфликты версий, повторные команды, расстановку и перемещения, недопустимую установку одного картриджа в два принтера, откат ошибочной замены, подписи/доступность фото, неизменность завершённой сверки, повторный импорт, SHA-256 резервной копии, восстановление, отзыв сеансов и хранение 14 копий.

После успешной сборки образа доступна дополнительная проверка Linux-контейнера:

```powershell
dotnet run --project RemoteAssist.Inventory.Server.Tests/RemoteAssist.Inventory.Server.Tests.csproj -- --container-smoke
```

Она создаёт собственный временный сертификат и тестовые каталоги, запускает контейнер без root с файловой системой образа только для чтения, проверяет HTTPS, запись базы и фото, перезапуск, резервную копию и восстановление. Проверка доверяет только своему конкретному временному сертификату; приложение такой обход TLS не использует. Тестовые контейнеры автоматически останавливаются. Тест не обращается к реальному NAS.

Официальные основания конфигурации: [TrueNAS — установка пользовательских приложений](https://www.truenas.com/docs/scale/apps/apps/), [SQLite — сетевой доступ через службу на машине с базой](https://www.sqlite.org/useovernet.html), [Microsoft — HTTPS в контейнере ASP.NET Core](https://learn.microsoft.com/en-us/aspnet/core/security/docker-https?view=aspnetcore-10.0).
