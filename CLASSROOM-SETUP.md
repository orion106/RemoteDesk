# Remote Desk: Windows 11 + Astra Linux 1.8

## Состояние поставки

Реализованы аудитории, удалённая помощь, питание и расписания, каталог программ, очистка локальных студенческих профилей Windows, мониторинг и журнал заданий. Приложение работает на Windows x64; .NET входит в переносимую сборку. Копируйте всю папку с `RemoteAssist.exe` и DLL. TigerVNC Viewer устанавливается отдельно на компьютере администратора.

В примерах используется условное имя **DC01-WS02**; замените его именем своего тестового ПК, разрешаемым через DNS. Проверка в реальном домене обязательна. Реальные подключения, переключение GRUB, удаление профиля и приёмка аудитории **ещё не выполнены**. Локальные тесты используют подставные адаптеры и не заменяют этот этап.

## Начать без API-токена GLPI

Выберите один из вариантов в разделе **Аудитории**:

1. **CSV из GLPI** — сохраните доступный вам список компьютеров из веб-интерфейса GLPI в CSV и выберите файл. Поддерживаются разделители `;`, запятая и табуляция, кавычки, UTF-8, UTF-16 с BOM и Windows-1251. Обязательная колонка — `Имя` или `Name`. Полезные колонки: `ID`, `UUID`, `Серийный номер`, `Расположение`, `IP`, `MAC`, `Операционная система`, `Место`, `Модель`. Если экспорт использует другие заголовки, переименуйте их в эти названия. Дату актуальности CSV нельзя считать временем живой проверки.
2. **Из Active Directory** — предварительно настройте подключение, область AD и маски в общем меню **Настройки**. Импорт получает имена компьютеров; аппаратные ID нужно подтвердить диагностикой.
3. **Карточка компьютера и настройка GRUB → Добавить компьютер** — укажите `DC01-WS02`, аудиторию `415`, место `02`, адреса Windows и Astra. Одинаковое DNS-имя в обоих полях допустимо. Введите только реальные MAC и аппаратные ID либо получите их диагностикой.

API-токен не нужен для опроса или управления компьютерами. Установленный GLPI Agent остаётся источником инвентаризации для GLPI, а управление Remote Desk выполняет через Windows/SSH. CSV повторно импортируется вручную, когда нужен свежий инвентарь.

Для необязательного API-импорта задайте в **Настройках классов** HTTPS-адрес GLPI, числовой ID сущности при необходимости и токены. Используется только чтение инвентаря REST API V1; сертификат должен быть доверенным. Права на сервере не расширяются. [Документация GLPI API](https://help.glpi-project.org/documentation/modules/configuration/general/api/api).

## Подготовка Windows

- Для Windows-адаптера используются учётные данные общего меню **Настройки → Подключение**. Нужны доступ к `\\DC01-WS02\C$`, WMI/DCOM `root\cimv2`, создание административного процесса и доступ WTS к сеансам. Системный диск этой версии адаптера — `C:`. WinRM не требуется.
- Для RDP Shadow и поиска сеансов нужны права текущей Windows-учётной записи, под которой запущен Remote Desk. Политика удалённого управления должна требовать согласия пользователя; приложение запускает Shadow без обхода согласия.
- Windows PowerShell 5.1 должен разрешать исполнение переданного административного сценария в соответствии с политиками организации. Remote Desk не передаёт `ExecutionPolicy Bypass`, не меняет политики, UAC или брандмауэр. При обязательной подписи сценариев эту сборку сначала нужно адаптировать под принятую процедуру подписания.
- Для определения вложенных доменных групп при очистке необходима доступность доменных служб. Если права владельца профиля проверить нельзя, профиль пропускается.

Сценарии и результаты отдельных заданий находятся в `C:\ProgramData\RemoteDesk\Jobs\<ID>`, с доступом для администраторов и SYSTEM. Успешные файлы опроса удаляются после чтения; результаты изменяющих операций сохраняются для сверки. Не удаляйте каталог неподтверждённого задания. MSI дополнительно оставляет `installer.log`.

## Подготовка Astra Linux 1.8

Нужны действующий SSH/SFTP, административный пользователь и заранее разрешённое выполнение `sudo -n python3` для временных сценариев. Это административный доступ к системе; он должен соответствовать принятой в институте модели прав. Если sudo требует пароль или операция запрещена средствами защиты Astra, диагностика завершится ошибкой — приложение не меняет эти настройки.

Для диагностики и питания используются Python 3, `loginctl`, `busctl`, `findmnt`, `lsblk`, `grub-editenv`, `grub-script-check`, `grub-reboot`. Для установки нужны APT/dpkg и уже настроенные репозитории. `smartctl` необязателен: без достоверного источника состояние диска показывается как отсутствие данных.

Для помощи и уведомлений нужны текущий **X11-сеанс**, `x11vnc`, `notify-send`, `zenity`, `runuser` и доступ к пользовательским DISPLAY/XAUTHORITY и D-Bus. Wayland и подключение к экрану входа этой версией не поддерживаются. Необходимые средства устанавливает администратор штатным способом из разрешённых источников; приложение их автоматически не добавляет.

1. На самом тестовом ПК сверяйте отпечаток используемого ключа SSH, например: `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub -E sha256`. Если сервер согласует другой тип ключа, нужен отпечаток именно этого ключа.
2. В **Настройках классов** задайте пользователя SSH, порт, пароль либо путь к закрытому ключу и его пароль. Сохраните настройки.
3. В карточке Astra укажите проверенный `SHA256:…`. Неизвестный или изменившийся ключ блокирует подключение; автоматического доверия первому ответу нет.
4. Укажите путь к внешнему TigerVNC `vncviewer.exe` на компьютере администратора.

Временные файлы хранятся в домашнем каталоге SSH-пользователя: `.remote-desk/<ID>`. Постоянной службы Remote Desk нет. Начатый установщик продолжает работать при разрыве SSH; повторно запускать его без сверки нельзя.

## Подтверждение физического ПК

После импорта или добавления сохраните карточку и выполните **Диагностика выбранного ПК**. При отсутствии доверенных UUID/серийного номера будет состояние **Идентичность не подтверждена**, а ответ покажет полученные аппаратные ID.

Сверьте имя, UUID и серийный номер с тестовым ПК, нажмите **Заполнить ID из проверки**, подтвердите данные, сохраните карточку и повторите диагностику. Для заполнения подходит ответ не старше двух минут. Имя, IP и наличие открытого порта не заменяют аппаратную идентичность.

Windows и Astra объединяются по непротиворечивым аппаратным ID. При неоднозначности отметьте ровно две проверенные карточки и нажмите **Объединить две записи**. Перед объединением сохраните подтверждённые одинаковые ID. Локальный номер места и порядок в сетке не перезаписываются импортом.

## Питание и испытание GRUB на DC01-WS02

Схема этой версии: GRUB по умолчанию запускает Astra; из Astra можно назначить Windows на одну загрузку, из Windows обычная перезагрузка возвращает Astra. Повторная загрузка Windows из Windows не реализована. **Загрузить Windows** при уже работающей Windows не перезагружает ПК.

Перед выключением или перезагрузкой отправляется предупреждение на 120 секунд. Отключённый сеанс, невозможность доставки уведомления или изменение состава сеансов откладывают действие. Windows использует мягкое завершение без `/f`; Astra проверяет блокировки выключения logind и не передаёт принудительные флаги systemctl. Сохранность несохранённой работы зависит также от поведения пользовательских приложений и самой ОС.

Испытание выполняйте с сохранёнными данными и локальным доступом к тестовому ПК:

1. Загрузите Astra обычным способом, выполните диагностику. Проверьте **GrubReady**, **GrubDefault**, **GrubStorage**, **WindowsMenuIds**, **BootConfigHash**. Автоматически ничего не исправляется. Нестандартная конфигурация, LVM/MDRAID, неподтверждённая файловая система, сохранение последнего выбора или непустой `next_entry` блокируют переключение.
2. До установки отметки испытания локально на тестовом ПК проверьте одноразовую загрузку: `sudo grub-reboot '<точный ID Windows из диагностики>'`. Угловые скобки и текст примера замените реальным ID. Прочитайте `sudo grub-editenv /boot/grub/grubenv list`, убедитесь в правильном `next_entry` и штатно перезагрузите компьютер после предупреждения пользователя.
3. Убедитесь, что запустилась Windows именно этого ПК. Затем выполните обычную перезагрузку Windows и убедитесь, что без ручного выбора загрузилась Astra. В Astra проверьте, что `next_entry` исчез/пуст. Если выбор остался, не включайте функцию переключения: конфигурация требует проверки администратором.
4. Повторите диагностику Astra в Remote Desk, скопируйте обнаруженный ID Windows в карточку, отметьте **Испытание одноразовой загрузки выполнено** и сохраните. Сохраняется отпечаток конфигурации, изменение которой потребует нового испытания. Отметку следует ставить для каждого проверенного ПК, а не переносить без проверки на весь класс.
5. Испытайте обе команды уже из приложения: **Загрузить Windows**, затем **Перезагрузить → Astra**. Успех требует живого ответа того же аппаратного ПК из целевой ОС с новым идентификатором загрузки. После пяти минут без подтверждения повторной перезагрузки нет.

Ограничения записи `grubenv`, из-за которых выбор может остаться постоянным, описаны в [документации grub-reboot](https://manpages.debian.org/bookworm/grub2-common/grub-reboot.8.en.html). Вложенные пункты GRUB требуют полного пути с ID подменю; текущий распознаватель рассчитан на обычный верхнеуровневый пункт Windows, поэтому нестандартные меню сначала проверяйте отдельно.

Для Wake-on-LAN задайте действительный MAC и broadcast нужной подсети. Поддержка должна быть заранее включена в прошивке/сетевом адаптере и разрешена сетью. Наличие MAC не доказывает готовности WoL; подтверждение — успешное пробуждение тестового ПК. **Включить → Windows** выполняет Wake-on-LAN, ожидает Astra, затем назначает Windows и перезагружает. Недоступность сети не считается доказательством выключения.

## Удалённая помощь

В Windows используется RDP Shadow с повторной проверкой владельца. Если сеансов несколько, выберите конкретный через **Главная**. В Astra запускаются одноразовый x11vnc только на loopback, SSH-туннель и TigerVNC Viewer. На X11-экране появляется запрос согласия; отказ и тайм-аут не открывают рабочий стол. Используется штатный режим [x11vnc accept popup](https://github.com/LibVNC/x11vnc/blob/master/doc/OPTIONS.md).

Закрытие Viewer или **Закрыть помощь Astra** закрывает созданный сервер и туннель и удаляет одноразовый пароль. При аварийном исчезновении консоли сервер закрывается после истечения 45-секундного продлеваемого срока. В журнале запуска Viewer не утверждается, что пользователь уже разрешил подключение.

Для перезапуска приложения сначала добавьте его ОС, полный путь и аргументы в разрешённый список в разделе **Программы**. Выполните диагностику, выберите конкретный процесс и приложение в **Мониторинг → Процессы**. Владелец получает запрос; после согласия проверяются процесс и сеанс. Принудительное закрытие спустя 15 секунд допускается только по этому отдельному согласованному запросу. Если прежнего пользователя/сеанс подтвердить нельзя, запуск не выполняется.

## Каталог программ

Задайте точную ОС, архитектуру, версию, источник и правило проверки. Для Windows это полный путь установленного EXE и его `FileVersion`; для Astra — имя пакета и точная версия dpkg. Заполняйте архитектуру по документации производителя, особенно для EXE-обёрток с несколькими архитектурами.

- MSI запускается с тихим режимом и подавлением перезагрузки. EXE требует проверенных для конкретного установщика параметров тихой установки и запрета перезагрузки, отмеченных администратором. Универсальных EXE-параметров нет.
- DEB передаётся по SFTP; проверяются SHA-256, имя, версия и архитектура. APT получает указанную версию из уже настроенных репозиториев; новые репозитории и ключи не добавляются.
- Файл выбирается в каталоге, фиксируется SHA-256 и повторно проверяется после передачи. Несовпадение блокирует запуск. Установщик может иметь собственные сценарии; неподтверждённые пакеты сначала испытывайте на тестовом ПК.
- Одновременно обрабатывается максимум четыре ПК. На одном физическом ПК изменяющие действия выполняются последовательно, включая «Нагрузку». Для другой ОС показывается требование загрузить её; автоматического переключения ради установки нет.
- Занятый пакетный менеджер, требование перезагрузки и неподтверждённая версия показываются отдельно. Отмена прекращает следующие действия, но не убивает уже работающий установщик.

## Очистка профилей Windows

По умолчанию список студентов пуст — кандидатов на удаление нет. Задайте конкретные логины или маски, например `student-*`, только если это действительно схема студенческих записей вашего института. Маска `*` запрещена. Сопоставление без учёта регистра; `*` — единственный шаблонный символ.

Отметьте тестовый ПК, сохраните правила и нажмите **Проверить профили отмеченных ПК**. Таблица показывает компьютер, логин, SID, путь и причину пропуска. Отметьте только специально созданный тестовый профиль; перед удалением проверьте содержимое. Встроенный администратор защищён по SID даже после переименования, также защищены `admin`, администраторы с вложенным членством, системные и загруженные профили. Неопределённые права означают пропуск.

Непосредственно перед удалением повторяются проверки. Используется только провайдер `Win32_UserProfile`; ручного удаления папок или веток реестра после ошибки нет. Учётные записи, сетевые домашние каталоги, перенаправленные папки и данные Astra не удаляются. Проверяются отсутствие локального профиля и соответствующей записи ProfileList. Механизм провайдера описан [Microsoft](https://devblogs.microsoft.com/scripting/conditional-user-profile-deletion-revisited/).

## Мониторинг, задания и хранение

Включите **Автоматический опрос** и сохраните режим. По умолчанию опрос — раз в 60 секунд, максимум восемь ПК одновременно, предупреждение по дискам — ниже 10%, по доступности — после трёх неудачных опросов. Набор служб настраивается отдельно для ОС, по умолчанию `glpi-agent`. Подробные процессы загружаются при диагностике. Состояние диска читается из Windows Storage/SMART только при подтверждённом сопоставлении; иначе данных нет.

История появления и устранения проблем сохраняется; одинаковые проблемы объединяются. Проблема незагруженной ОС не считается устранённой только потому, что загрузилась другая. После запроса выключения ожидаемая недоступность учитывается 24 часа, Wake-on-LAN снимает это ожидание.

Разовые/еженедельные расписания питания создаются для отмеченных компьютеров. Приложение должно оставаться открытым, допустимо свёрнутым. Запуски, пропущенные при закрытом приложении или надолго задержанные, отмечаются как пропущенные и не выполняются задним числом. Службы планировщика в ОС не устанавливаются.

После обрыва связи откройте **Задания**, выберите строку и нажмите **Сверить выбранное задание**. Сверка читает сохранённый результат/фактическую загрузку и не повторяет команду. Неподтверждённая установка, очистка, перезапуск приложения или отправленная команда питания блокируют новые изменения этого ПК. Для чтения результата установки нужна ОС, в которой она выполнялась. Факт выключения невозможно достоверно установить по отсутствию сетевого ответа; после нового подтверждённого запуска прежняя команда уже не выполняется, но исторический успех выключения не утверждается.

Настройки: `%LOCALAPPDATA%\RemoteAssist\settings.json`. Реестр компьютеров, профили ОС, пакеты, задания, расписания и история проблем: `%LOCALAPPDATA%\RemoteAssist\lab.db` (SQLite). Для резервной копии закройте приложение и скопируйте каталог RemoteAssist. Не заменяйте базу во время работы. Пароли и токены — в Windows Credential Manager текущего пользователя, отдельно от JSON/SQLite; при переносе на другой компьютер их нужно ввести заново. Закрытые SSH-ключи остаются в указанном вами файле.

## Приёмка перед использованием в аудитории

На **DC01-WS02** проверить:

- Обе ОС отвечают с теми же UUID/серийным номером; смена IP не создаёт новую физическую карточку; ответ чужого ПК блокирует управление.
- Отказ/тайм-аут и согласие на RDP Shadow и X11VNC; после закрытия помощи отсутствуют созданные туннель, сервер VNC и временный пароль.
- Доставку предупреждения 120 секунд, отказ при недоступном/отключённом сеансе, WoL, обе стороны загрузки, очистку `next_entry` и отсутствие повторных перезагрузок по тайм-ауту.
- Установку контрольного MSI/EXE/DEB/APT, неверную сумму, неверную ОС/архитектуру, занятый пакетный менеджер, требование перезагрузки и обрыв связи с последующей сверкой.
- Удаление только специально созданного незагруженного студенческого профиля при сохранении самой учётной записи. Проверить отказ для `admin`, переименованного RID-500, вложенной административной группы и профиля, вошедшего в сеанс после предпросмотра.
- Мониторинг и расписание в свёрнутом приложении, отсутствие заднего выполнения после закрытия, журнал и блокировку одновременно запущенного обновления «Нагрузки» на том же ПК.

После успешной проверки одного ПК повторите приёмку на одной аудитории с её DNS, VLAN, broadcast и политиками. Массовые операции включайте после этой проверки. Здесь не проставлены фиктивные отметки успешной сетевой приёмки.
